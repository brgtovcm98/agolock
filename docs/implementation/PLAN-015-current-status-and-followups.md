## 2. 검증 증거와 한계

| 검증 | 결과와 해석 |

실제 API 실행 시 독립 로컬 DB `agolock_inventory_live_20261024`에 V25까지 적용했습니다. 임시 API 프로세스는 종료했으며 테스트 DB는 남아 있습니다. `/tmp/agolock-inventory-*` 로그는 세션 임시 증거이므로 다음 작업에서 보존을 가정하지 않습니다. 최종 판단은 다시 생성한 결과와 커밋 기준으로 남깁니다.

## 3. 남은 물건·재고 개선

우선순위는 다음 실행 순서입니다. 아래 항목은 모두 미완료이며, 기능 추가와 검증 공백을 구분합니다.

| ID·우선순위 | 현재 상태·수정 대상 | 완료 조건 |
|---|---|---|
| INV-01 · 높음 | `frontend/e2e/inventory-live.spec.ts` 시간 초과. 초기에는 재사용된 Vite가 다른 API를 보거나 숨겨진 버튼을 선택하는 문제가 있었고, 이를 분리한 뒤에도 편집 화면에서 시간 초과가 남음. 원인 단정 금지 | 최신 API 실행 파일과 독립 DB·포트로 재현, 단계별 요청·브라우저 오류·trace 확인. 모킹 없이 소유/공유 MANAGE 등록·빈 설명/0원 편집·이동이 데스크톱/모바일에서 성공 |
| INV-02 · 높음 | 항목 워크트리에서 175개 단일 실행 연속 2회 통과. 테스트 컨테이너를 테스트 JVM당 한 쌍으로 공유하도록 수정했고([PLAN-016 6.1](PLAN-016-item-workflow-and-queue.md)), 남은 것은 현재 HEAD의 `full` 검증 기록과 리뷰 승인·병합 | 동일 커밋의 깨끗한 환경에서 전체 백엔드·계약·프론트·브라우저 검사를 한 번에 통과하고 환경·명령·결과 보존 |
| INV-03 · 중간 | `InventoryCommands.kt`가 여전히 값과 `*Present` Boolean을 병렬 보관. 계획의 내부 명령 타입화는 미반영 | HTTP의 생략/null 의미를 유지하면서 내부 명령을 유지/설정의 명시적 타입으로 변환. 기존 API와 회귀 테스트 보존 |
| INV-04 · 중간 | `features/inventory/api.ts`의 Item 권한·공유 필드는 선택적이며 상세 화면에 소유자 추측 fallback이 남음 | 승인 구현 스키마에 맞춰 필수 타입과 실제 호출부를 정리하고 누락 응답·권한 UI 검증 |
| INV-05 · 중간 | `InventoryResponseAssembler`의 단건 응답은 DB 조회를 포함하고 목록 응답과 effective 값 조립이 중복됨 | 조회와 순수 응답 계산을 분리하고 단건·목록의 상속/null/빈 문자열·위치 의미가 같음을 검증 |
| INV-06 · 중간 | SQL 집계·페이지 처리는 반영됐지만 변경 후 권한 조회 수·규모별 지연의 전용 측정 기록은 없음. 일부 선택기는 `collectPages`로 모든 페이지를 모음 | 재고·위치·카테고리 증가에 따른 SQL 횟수·메모리·초기 화면 지연 측정. 필요할 때만 검색/점진 조회로 개선 |
| INV-07 · 배포 전 | V25는 새 DB 적용·순수 정규화 충돌 테스트를 확인했으나 기존 데이터 충돌과 중단 후 재실행 리허설은 별도 | 기존 데이터 복사본에서 충돌 ID 보고·무변경 중단·명시적 병합 후 재실행을 검증. 자동 병합 금지 |
| INV-08 · 낮음 | 프론트 빌드의 500kB 초과 번들 경고가 남음 | 실제 로딩 측정 후 화면별 코드 분할 필요 여부 결정. 경고 임계값을 올려 해결하지 않음 |

재현 시 `VITE_API_TARGET`과 이미 떠 있는 `127.0.0.1:5173` 서버의 대상 API가 같은지 먼저 확인합니다. 실제 시나리오는 `INVENTORY_LIVE=1`과 SMTP/Mailpit이 필요하며, 기본 모킹 E2E의 성공을 대신 사용할 수 없습니다.

최신 API를 별도 DB·`8087` 포트에서 실행하고 가입 설정·SMTP/Mailpit이 준비된 경우의 브라우저 재현 명령입니다. `5173`에 기존 서버가 있으면 그 서버가 동일 API를 바라보는지 확인한 뒤 실행합니다. 이 명령 자체를 성공 증거로 간주하지 않습니다.

```bash
INVENTORY_LIVE=1 VITE_API_TARGET=http://127.0.0.1:8087 pnpm --filter @agolock/frontend exec playwright test e2e/inventory-live.spec.ts --project=desktop-chromium --workers=1 --trace on
```

성공한 뒤 `mobile-chromium`도 같은 조건으로 확인하고, 실패 시 첫 미완료 동작·요청/응답·console과 trace를 기록합니다.

## 5. 다음 실행 순서

항목 단위 실행·검증·리뷰·병합 규약과 전체 대기열은 [PLAN-016](PLAN-016-item-workflow-and-queue.md)을 따릅니다. 병합 게이트가 현재 HEAD의 전체 검증 pass를 요구하므로, 백엔드 전체 실행이 green이 되는 INV-02를 먼저 처리하고 INV-01을 이어서 실행합니다.

1. INV-02로 같은 커밋의 전체 검증을 확보해 병합 게이트를 green으로 만듭니다.
2. INV-01 실제 API 시간 초과 원인과 성공 경로를 확인합니다.
3. INV-03~07을 순차 개선합니다. INV-08은 측정 결과로 필요 여부를 결정합니다.
4. REL-01~06의 기능·계약·이미지·UI 후속을 마감합니다. 세부 규칙은 해당 원본 문서를 갱신합니다.
5. VPS 접속·도메인·시크릿이 준비되면 REL-07~08을 실행합니다. 검증 전 출시 완료로 표시하지 않습니다.
6. REL-09에서 통합·원격 반영 상태와 검증 커밋을 갱신합니다.

이 문서는 작업 목록의 단일 입구입니다. 새 코드 변경 후에는 해당 기능 문서와 검증 근거를 함께 갱신하고, 완료한 항목만 상태를 변경합니다.
