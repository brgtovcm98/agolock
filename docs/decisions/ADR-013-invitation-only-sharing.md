# ADR-013: 초대 전용 공유

- 상태: 승인됨
- 날짜: 2026-10-20

## 맥락

제품 요구사항은 공유가 이메일 초대와 수락 후 효력을 가진다고 정의합니다. 반면 API에는 즉시 효력이 있는 직접 공유 엔드포인트가 있었고, 미가입 이메일에는 `share.grantee_user_id`가 NOT NULL이라 직접 공유가 성립하지 않았습니다. 공유받은 사용자에게는 수락 전 접근 권한이 없어야 합니다.

## 결정

- 1차 공유는 초대 전용입니다.
- 소유자는 `POST /share-invitations`로 초대를 만들고, 초대받은 사용자가 수락하면 Grant를 생성합니다.
- 직접 공유 `POST /shares`는 1차 공개 API에서 제거하고 3차에서 재검토합니다.
- 초대 토큰은 해시로 저장하고 1회 사용하며 기본 만료는 7일입니다.
- 수락하는 계정의 이메일은 초대 이메일과 일치해야 합니다.
- 초대받은 사용자는 초대를 거절할 수 있으며 `DECLINED` 상태를 기록합니다.
- 같은 리소스와 이메일에 대기 중인 초대가 있으면 중복 생성하지 않고 `409 INVITATION_ALREADY_PENDING`을 반환합니다.
- 이미 활성 Grant가 있으면 초대를 만들지 않고 `409 SHARE_ALREADY_EXISTS`를 반환합니다.
- 자기 자신이나 Space 소유자를 초대할 수 없습니다.
- 만료된 초대는 정리 job이 `EXPIRED`로 표시합니다.

## 결과

- 공유 효력 시점이 명확해지고 수락 전 접근이 차단됩니다.
- 초대 목록, 받은 초대 목록, 거절 흐름이 필요합니다.
- 기존 가입자에게 즉시 공유하는 UX는 1차에서 제공하지 않습니다.
- 직접 공유가 필요하면 3차에서 별도 동의·철회 규칙과 함께 재검토합니다.

## 대안

- 직접 공유와 초대를 모두 지원: 두 경로의 효력과 철회 규칙이 달라집니다.
- 초대 없이 이메일로 즉시 Grant 생성: 수락 전 접근 차단 요구와 충돌합니다.
- 초대 토큰을 평문 저장: 유출 시 재사용 위험이 커집니다.
